# Decisions

Calls made while building N7 from the PRD (`docs/prd-meeting-follow-up.md`, source of truth: https://claude.ai/artifact/4jQyEmkGRx8SDcAYMijeJn). The PRD's own decisions D-01 to D-06 are fixed and are not repeated here; this log numbers repo decisions D-1, D-2, ... Rows marked **confirm** were open for Shane; all 13 were confirmed by Shane on 2026-11-25 (PR #1 review), including D-6's model id `claude-sonnet-5-5`.

All rows below were taken 2026-11-24 by the unattended kickoff build (no one was available to ask), as the most reasonable reading of the PRD.

| Id | Decision | Why | Status |
|---|---|---|---|
| D-1 | **The kickoff build ran unattended and could not use the `add_repo` tool** (not available in the session). The repo was already in the session's GitHub scope, so it was cloned and pushed directly. | Same effect as `add_repo`; noted so the run log is complete. | taken |
| D-2 | **Repo shape follows N1 (`speed-to-lead`):** logic in `src/*.js` (CommonJS, no dependencies), unit tests with `node --test`, and a build script (`scripts/build-workflow.js`) that inlines `src/` and `prompts/` into the n8n Code nodes, like N1's `scripts/build_phase2.py`. One `workflow.json` at the root, as the PRD kickoff lists. | Tested code and the exported workflow cannot drift: `npm run check` fails if `workflow.json` is stale. | taken |
| D-3 | **Work lands on branch `kickoff` as one draft PR**, not on `main`. The PRD kickoff step 6 says "Commit on main, push"; the build brief for this run allows only a README stub on `main`. | The run's own rules win over the kickoff text for git handling. Merge is Shane's call. | taken |
| D-4 | **No live n8n, HubSpot, Drive, Gmail or model call was made.** Kickoff step 3 ("build the workflow in n8n") and step 4 ("run the fixtures") are done offline: `workflow.json` is generated and executed by a small interpreter (`test/n8n-sim.js`) against in-memory fakes; the model is replaced by hand-written recorded responses. | The run was files-only by rule. What this proves and does not prove is spelled out in `docs/EVAL.md` and `docs/ACCEPTANCE.md`. | taken |
| D-5 | **Model call through the HTTP Request node to the Anthropic Messages API with a forced tool** (`record_meeting`, `input_schema` = `prompts/extract.schema.json`), not n8n's Anthropic chat node with the Structured Output parser that PRD §3 names. Validation is then done in a Code node by `src/schema.js`, stricter than the parser (extra keys fail). | N1's pattern; the raw response (including token usage for cost) is available; the validator is unit-tested and cross-checked against the JSON Schema with Ajv. PRD D-03's intent (schema-validated before anything is written, failures to Needs-Review with raw output) is kept. | confirmed (Shane, 2026-11-25) |
| D-6 | **Model id `claude-sonnet-5-5`** in the config node, from PRD §6 item 1 ("Claude Sonnet 5.5"). The exact API id string was not checkable offline. | Default taken from the PRD; the string must match what the Anthropic console lists. | confirmed (Shane, 2026-11-25) |
| D-7 | **Long transcripts:** over `chunkChars` (60,000) the text is split on speaker turns, each chunk gets the same extraction call (map), then one reduce call merges the chunk records (`prompts/reduce.md`). Checks always run against the full transcript. PRD D-03's "one model call" therefore holds for transcripts up to 60,000 characters; a chunked file costs chunks + 1 calls, all counted against the daily cap. | PRD §1 step 2 asks for map then reduce; quotes must stay verbatim, so the map step extracts rather than paraphrases. | taken |
| D-8 | **`.docx` is read in a Code node** (`src/docx.js`: reads `word/document.xml` from the zip with zlib), not "n8n's extract node". As far as this build could tell, n8n's Extract From File node has no `.docx` operation. Needs `NODE_FUNCTION_ALLOW_BUILTIN=crypto,zlib` on the n8n process. | PRD §1 step 2 lists `.docx`. If Shane's n8n version has a docx operation, this can be swapped. | confirmed (Shane, 2026-11-25) |
| D-9 | **Google Docs in the Inbox are accepted too** (Google Meet saves transcripts as Google Docs): exported as plain text through the Drive API. | PRD §6 item 5 defaults to Google Meet and Zoom exports; a Meet transcript is a Google Doc unless downloaded. | taken |
| D-10 | **Trigger is a Schedule node every 5 minutes that lists `Meetings/Inbox`**, plus a manual trigger, not the Google Drive "watch folder" trigger. One file is processed per execution; when more remain, the workflow calls itself (`Process next file`). The workflow is exported inactive. | A Drive "file created" trigger does not fire when a person moves a file back from Needs-Review (PRD §2's `.match.json` flow), and listing the folder covers both. Kickoff step 6: leave it manual until Shane turns it on. | taken |
| D-11 | **Idempotency key is the Drive file id, with a SHA-256 of the normalised text as a second key**, so a re-uploaded copy (new file id) still finds its ledger row and updates the same note and draft. | PRD D-06 keys on file id; demo step 6 says "re-drop", which in Drive usually means a new upload. A hash is not transcript text, so PRD §4 PII holds. | taken |
| D-12 | **The ledger is the Google Sheet tab `processed`, read and written through the Sheets API using the Google Drive OAuth2 credential** (the Drive scope covers Sheets), so Google needs one credential, not two. Columns: `src/ledger.js` `COLUMNS`. Every value is checked to be an id, a number or a code from a fixed list; free text is refused. | PRD §4: the sheet row holds ids and a status, not text. | taken |
| D-13 | **Draft update path:** new drafts use the Gmail node (Create draft); a re-run updates the existing draft with an HTTP `PUT .../drafts/{id}` (the Gmail node has no draft update). If the draft is gone (sent or deleted by a person), it is not recreated; the ledger records `draft_state = gone`. | PRD D-06 wants update, not duplicate; a gone draft means a person already acted on it. | taken |
| D-14 | **Recipients are computed in code, never taken from the model:** an attendee is a recipient only if their email appears in the transcript's header block (the lines before the first `Name:` speaker turn, or a `.vtt` NOTE block; with no `Name:` turns at all, only the leading `Title:`/`Date:`/`Attendees:`-style lines) and is not one of `ownDomains`. An address spoken or pasted in the body, including a pasted `Attendees:` line, never becomes a recipient or a rule-1 match key (tested). No recipients → no draft (`draft_state = no_recipients`), the note is still written. | PRD §1 step 7 and §4 ("never to anyone not named"); also the main prompt-injection guard. | taken |
| D-15 | **No text that can reach the draft may contain a link or an email address** (reason `followup_link`): the title (it becomes the subject), `followUp.subject` and `.body`, action-item tasks and owner names, attendee names. Links are scheme URLs, `www.`, `host/path` and bare hosts on common TLDs. This is in addition to PRD §3's bracket/TBD/insert/placeholder check on the body (whole words, case-insensitive). Either failure sends the file to Needs-Review with nothing written. | A pasted instruction in a transcript can carry a payment link; a person can add real links when sending. | confirmed (Shane, 2026-11-25) |
| D-16 | **HubSpot searches use `EQ` on `domain`, `dealname`, `name` and contact `email`, at most 5 values each** (HubSpot's limit of 5 OR-ed filter groups); extra domains or mentions are dropped and listed in the run's `skipped` field. An empty list searches for a value no record has, never an unfiltered search. | PRD §2: never match on a fuzzy name. | taken |
| D-17 | **Rule 1 with several companies falls through to rules 2 and 3**; rule 2 matches only when the single deal hit has exactly one associated company; Needs-Review candidates are rule-3 hits first, then rule-1 hits, at most 3. After any company match, the deal is attached only if the single deal hit belongs to that company. | PRD §2: "the first rule that yields exactly one company wins"; candidates "from rule 3". | taken |
| D-18 | **Every miss of a quote, company mention or deal reference costs 0.1 of `confidence.actionItems`**; three misses of any kind fail the file (`unverified_quotes`). | Literal reading of PRD §3 ("A miss drops that item and lowers..."). | taken |
| D-19 | **Low confidence (`confidence.summary` < 0.6): the note is written with a "Low confidence" line and the draft is created; the file then goes to Needs-Review** with a sidecar. | PRD §3 says the note is still written; a draft is only a draft. | confirmed (Shane, 2026-11-25) |
| D-20 | **Alerts never use email.** Errors go to an `errors` tab in the ledger sheet and, if `alertWebhookUrl` is set (for example a Slack incoming webhook), one throttled line (at most one per 15 minutes) to that URL. Empty by default. The workflow is its own error workflow (Error Trigger node). Failed HubSpot or Gmail writes (after 3 tries) send the file to Needs-Review with reason `hubspot_error` or `gmail_error`. | PRD §4 "failure is a folder"; "zero sends" must hold for alerts too; PRD §6 item 2 says no digest in v0.1. | taken |
| D-21 | **Cost is computed from response token usage times two config prices** (`priceInputPerMTokUsd`, `priceOutputPerMTokUsd`), which are `null` until Shane fills them. While null, `cost_usd` stays empty and tokens are still logged. The PRD's "under $0.10 per run" is a target, not measured. | No price was supplied, and this run could not check current prices. | confirmed (Shane, 2026-11-25) |
| D-22 | **Per-file token ceiling default 100,000 estimated input tokens** (characters / 4), daily cap 50 model calls (PRD default). A file over the ceiling stays in Inbox, gets a `waiting/token_ceiling` ledger row and is skipped until the row is removed; over the daily cap, nothing runs until the next day (UTC). | PRD §4 gives the cap but no ceiling value. The 90-minute fixture is about 21,000 estimated tokens. | confirmed (Shane, 2026-11-25) |
| D-23 | **Four credentials, not three:** `google-drive-lab` (Google Drive OAuth2, also used for Sheets), `gmail-lab`, `hubspot-demo`, and `anthropic-lab` for the model. | PRD §5 acceptance says "three credentials"; the model call needs a key too (the PRD's Anthropic node would need one as well). | confirmed (Shane, 2026-11-25) |
| D-24 | **Fixture companies are new fictional records** (`fixtures/hubspot-seed.json`: 9 companies, 2 deals, 5 contacts on `.example` domains), not the N1/N2 demo records: N1 seeded contacts only and N2 one company, so most fixture companies must be loaded into the demo portal before a live run. | PRD §5 says "across the demo HubSpot companies loaded for N1 and N2"; those do not cover eight meetings. | confirmed (Shane, 2026-11-25) |
| D-25 | **Filler dialogue in the fixtures is generated** (seeded, `fixtures/build.js`) around hand-written content lines, to reach the PRD's 20 to 60 minute lengths (at 150 words a minute) and 90 minutes for the chunking fixture. The answer keys (`fixtures/expected/`) are hand-written. | Writing eight hour-long transcripts by hand was not proportionate; the content that is scored is hand-written. | taken |
| D-26 | **The two-company fixture (F04) yields two candidates, not three.** PRD §5 demo step 5 says "three candidates"; §5 test data says the fixture "names two companies". DEMO.md says "its candidates (two in this fixture)". | The test-data spec is more specific. | taken |
| D-27 | **Tests and CI are added** (GitHub Actions running `npm run gate` on Node 22: lint, build drift check, tests). N1 and N2 have no CI (`.github/` is absent in both). | The build brief asks for CI; it mirrors N1's local gate rather than any N1 workflow file. | taken |
| D-28 | **n8n execution data: successful executions are not saved** (`saveDataSuccessExecution: none`); errors and manual runs are. Error runs still keep data for debugging, which can include transcript text. | confirmed (Shane, 2026-11-25) |
| D-29 | **Defaults taken for PRD §6:** (1) model Sonnet 5.5, see D-6; (2) no digest in v0.1, see D-20; (3) no contact creation; attendees with an email and no HubSpot contact are listed in the note as "Attendees not in CRM"; (4) Drive folder ids are config values, so the Lab Intelligence Workspace shared drive works (`supportsAllDrives` is set on every Drive call); (5) fixtures cover Google Meet style (`.vtt` with `<v>` tags, D-9 Google Docs) and Zoom style (`.vtt` with `Name:` cue text, unit-tested) plus `.txt`, `.md` and `.docx` (unit-tested). | PRD §6 defaults. | confirmed (Shane, 2026-11-25) |
| D-30 | **A `.match.json` override re-runs extraction** (one more model call) rather than reusing the summary saved in the sidecar. | One code path; the cost is one call. | taken |
| D-31 | **The `processed` ledger counts model calls per row**, so a re-run on the same day overwrites that row's call count and the daily cap can undercount by the earlier run's calls. | Kept simple for v0.1; noted as a known limit. | taken |
| D-32 | **A run claims its transcript first by moving it from `Inbox` to a fourth folder, `Meetings/Processing`**, and moves it to `Processed`, `Needs-Review` or back to `Inbox` (spend waits) at the end. A run that starts meanwhile (the 5-minute schedule overlapping a chained or slow run) no longer sees the file. The window between listing and claiming is a second or two, not closed. A crash mid-run leaves the file in `Processing` (and an `errors` row); a person moves it back. | Found in review: without a claim, overlapping runs created duplicate notes and drafts (breaks PRD D-06). PRD D-01 names two destination folders; this adds a third. | confirmed (Shane, 2026-11-25) |
| D-33 | **Create draft does not auto-retry** (every other external call retries 3 times). A failure goes to Needs-Review (`gmail_error`) with the note id kept, so moving the file back retries cleanly. | A create that timed out but succeeded would leave a second draft. | taken |
| D-34 | **The ledger row is written before the sidecar upload and the file moves**, so a failure in the tail cannot leave a note and draft that no row records. | Found in review. | taken |
| D-35 | **A re-run that matches a different company than the ledger row** (for example a `.match.json` after a done run) **writes a new note on the new company**; the old note stays where it was for a person to delete (the key has no delete scope). | D-36 | **A failed Drive download (transcript or `.match.json`) routes the file to Needs-Review** (`unreadable` / `override_invalid`) instead of stopping the run, so one bad file cannot block the queue. | Found in review; PRD §4 "failure is a folder". | taken |
